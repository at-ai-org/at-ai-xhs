# 视频号会话：怎么保持、掉了怎么办

> 适用：`uploader/tencent_uploader/`（视频号 / 微信视频号助手）。实现集中在
> `uploader/tencent_uploader/session.py`。

## 一、先说结论

**视频号没有"续期"这回事，上游也没有。**

> 📌 补充（2026-09-30）：**全局的「账号会话定时续期」已经做了**，见
> [`myUtils/session_renew.py`](../myUtils/session_renew.py) 和 README 的「账号会话定时续期」一节：
> 默认每天 0 / 7 / 14 / 20 点，对「账号管理」里的**全部账号**（含视频号）跑一轮
> `check_cookie`，视频号走的正是本文这套「持久化 profile + 回写 cookie」。
> 标题那句说的是**上游没有**，以及**续期不等于把 cookie 文件上的 `expires` 往后挪**——
> 能做的只有"定期真去用一次"，把服务端会话拖住。

扫码登录拿到的是微信服务端的一条会话（cookie 只有 `sessionid` + `wxuin`）。本地 cookie 上的
`expires` 是登录时刻 +400 天，跟它什么时候被作废**毫无关系**——所以判断死活只能真开浏览器试，
不能读文件。

上游 `dreammis/social-auto-upload` 全历史 327 个提交里，`launch_persistent_context` /
`user_data_dir` / `保活` / `续期` 的命中数都是 **0**。它只在两个地方写过 cookie
（登录成功后、发布成功后各一次 `storage_state`），没有任何保活逻辑。

本项目实测到的掉线时间线（改造前的真实日志）：

| 时间 | 事件 |
| --- | --- |
| 09-25 20:20 | 扫码成功，账号文件 `7841fac8-….json` |
| 09-25 20:44 ~ 22:30 | 多轮校验全部「cookie 有效」，期间两次发布成功 |
| 09-26 08:19 | 校验开始全部失败 |
| 09-26 08:54 | 发布任务直接失败：`cookie文件已失效，请先完成视频号登录` |
| 09-26 08:57 | 删掉旧账号、重新扫码 |

**本地文件毫发无损，服务端会话在约 10 小时里被作废了。**

## 二、现在怎么做的（三件事）

1. **每条用过的路径都回写 cookie**——校验、失败、异常一律回写。
   改造前只有「发布成功」那最后一行会写（`main.py` 的 `storage_state(path=…)`），
   校验过程里服务端下发的任何新票据都被丢掉了。
2. **持久化浏览器 profile 取代一次性 context**。cookie 罐、localStorage、IndexedDB 都留在
   `cookies/tencent_uploader/uin_<微信号>/`，登录、校验、发布是同一个"设备"。
   目录按**微信号（wxuin）**命名，所以重新扫码也是回到同一台设备上。
3. **登录 / 校验 / 发布共用一套启动参数**（`session.build_launch_kwargs()` 是唯一来源）：
   patchright + 真 Chrome（`channel="chrome"`）+ `no_viewport` + 防检测脚本。
   改造前登录用 `--lang en-GB`、校验不加语言、发布连防检测脚本都没有——同一张票在三种
   指纹下使用。

顺带两个细节：

* `launch_persistent_context` **不接受** `storage_state` 参数，所以"账号 JSON 灌进 profile"
  是起完浏览器再 `add_cookies`（`session.seed_cookies`），规则是 **JSON 是唯一权威**：
  同名 cookie 直接覆盖，profile 里其它域的设备票据继续留着；
* 账号 JSON 现在还会带上 profile 里积累的 localStorage（含站点自己的
  `_finger_print_device_id`），不再是一份"每次都是新设备"的薄快照。

## 三、A/B 开关

`conf.py`（本地配置，不进版本库；模板见 `conf.example.py`）：

```python
TENCENT_HEADLESS = True       # 视频号 登录/校验/发布 三处共用；False = 全部有头
TENCENT_PROFILE_ROOT = BASE_DIR / "cookies" / "tencent_uploader"
```

不改文件也能临时试：

```bash
SAU_TENCENT_HEADLESS=0 ./start.sh      # 有头跑一阵，对比掉线频率
```

为什么要留这个开关：上游抖音踩过"无头撞反爬 → 校验误报 cookie 失效"的坑
（upstream commit `914a5f0`，注释里写着"实测登录刚成功 90s 后校验即失败"），
patchright 官方的最佳实践也建议 `headless=False`。视频号要不要照做**还没有定论**，
所以做成开关，用一段时间的数据说话。

## 四、日常怎么用 / 怎么排查

| 想做什么 | 怎么做 |
| --- | --- |
| 看某个账号用的哪个 profile | 日志里搜 `uin_`，或直接看 `cookies/tencent_uploader/` |
| 让某个账号"换一台设备" | 删掉 `cookies/tencent_uploader/uin_<微信号>/`，下次任务会重建 |
| 确认是不是真掉线 | 看日志：`cookie 已失效（页面跳转到登录页）` = 真失效；`cookie 有效` = 还活着 |
| 账号正被发布任务占用时的校验 | 日志出现 `🕐 … 正被其它任务占用…本次校验用只读方式`，这是正常的降级，不是错误 |
| **账号正常、却拿不到账号数据** | 先看 `cookies/tencent_uploader/` 有没有 `_login_*` 目录冒出来——**有就说明取数用错了 profile**（`seed=False` 会落到空白的临时 profile 上，页面整页跳登录页，报"未登录"）。2026-10-09 修过：`tencent_session` 现在直接拒绝「传了 `account_file` 又 `seed=False` 又不给 `profile_dir`」这个组合，取数显式传 `profile_dir_for(account_file)`。这类"账号好的但报未登录"**别急着重新扫码**，扫码解决不了 |
| 重新扫码 | 账号管理页「添加账号」（Web）或 `sau tencent login --account <名字>`（CLI） |

## 五、已知代价与边界

* **校验每次固定花掉 8 秒**：等的是"页面被 JS 跳转到 login.html"，跳转不发生就得等满
  超时（这是上游 `662633b` 的修法，为了不误报" cookie 有效"）。账号管理页每次刷新会逐账号
  校验，账号多时较慢——正解是给 `/getValidAccounts` 加缓存（本次未做）。
* **profile 目录跨进程靠 Chrome 单例锁保护**：同进程靠 `myUtils.browser_lock`，
  跨进程（后台在发布、同时用 CLI）会由 Chrome 自己报 "profile is already in use"，
  不会写坏数据。上次被强杀留下的锁会在下次启动时自动清掉（`session.cleanup_stale_lock`）。
* **不承诺永不掉线**：微信服务端随时可以作废会话（换设备、别处登录、风控）。
  这套改动的目标是"尽量拖住 + 掉了一分钟内就能看出来 + 一键重扫"，
  而不是"永不过期"。

## 六、改造时的实测记录

| 验证项 | 结果 |
| --- | --- |
| 空 profile + 账号 JSON 注入 cookie 后校验 | 有效（证明 `add_cookies` 注入生效） |
| profile 复用（第二次校验） | 有效 |
| 发布入口（首页 → 点「发表视频」→ 表单） | `input[type=file]` 与短标题框都在，未被跳登录页 |
| 扫码登录路径（新的统一启动参数） | 二维码正常提取并可解码（已去掉 `--lang en-GB`） |
| 登录失败清理 | 临时 profile 目录、二维码文件都被清掉，没留垃圾 |
| profile 被占用时的校验降级 | 不排队（0.9s~19s 内返回正确结论），不会让账号页干等发布跑完 |
| 账号 JSON 回写 | 每次校验/发布后更新，且比改造前多带 localStorage 设备指纹 |
