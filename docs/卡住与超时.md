# 卡住、超时与资源回收

这份文档记录一个核心事实和围绕它的防护措施。**遇到"任务一直卡着"先看这里。**

自动的四层防护之外，还有一层**用户触发**的：发布中心每个任务都能手动中断，
见「[手动中断](#手动中断用户触发2026-09-新增)」——不用再等 30 分钟看门狗。

## 核心事实：线程杀不掉

发布是**阻塞式**浏览器自动化。"卡住"通常不是死循环，而是**在等一个永远不会来的东西**：

* 等一把没人会释放的锁；
* 等一个已经不再响应的浏览器驱动（实测最常见的是 `context.close()` 一直 await）。

这类状态**既不抛异常也不超时**——任务会永远停在「发布中」，批次也永远不 `done`。
而 Python **没有安全中断线程的办法**，所以一旦卡住，那个线程就收不回来了。

既然杀不掉，能做的是两件事：

1. **让等待本身有上限**，这样最坏情况是"几分钟后带着明确原因失败"，而不是无限期挂着；
2. **把结论改对**，让界面、批次、记录都如实反映"它卡住了"，而不是假装还在跑。

## 四层防护

从内到外，按触发顺序：

| 层 | 位置 | 默认 | 作用 |
|---|---|---|---|
| 1. 收尾超时 | `uploader/tencent_uploader/session.py` | 30s | 回写 cookie / 关浏览器最多等这么久，超时就放弃。**保证锁一定释放** |
| 2. 等锁上限 | `myUtils/browser_lock.py`、`tencent_uploader/session.py` | 10min | 等账号锁 / 并发名额 / 视频号 profile 锁超时就抛 `BrowserLockTimeout` |
| 3. 任务看门狗 | `sau_backend_publish.py`、`sau_backend_xhs.py` | 30min | 任务跑太久就判失败；**两个入口都有** |
| 4. 启动收尾 | `myUtils/publish_records.py` → `sau_backend.py` | — | 进程启动时把上次残留的「排队中/发布中」记录标成「已中断」 |

第 1、2 层的保护对**所有**开浏览器的路径自动生效（都走 `browser_session`）；
第 3 层要各自适配，因为两边的任务模型不一样：

| | 发布中心 | 小红书工作台 |
|---|---|---|
| 任务模型 | `status` + 通道队列（同一账号一条通道，串行） | `state` + 一个任务一个线程，没有队列 |
| 看门狗 | `_arm_watchdog` / `_finish_task` | `_arm_xhs_watchdog` / `_task_finish` |
| 卡死后还要做什么 | 通过 `Event` **通知通道**放弃线程、继续下一个任务 | 无队列，只需把任务和发布记录一起收尾 |
| 超时开关 | `SAU_PUBLISH_TASK_TIMEOUT` | 同一个开关（有测试钉着两边相等） |

### 第 1 层为什么必须存在

收尾动作跑在 `with lock:` 里面（视频号 profile 锁）。任何一步不返回，**锁就永远不释放**，
之后这个账号的每次发布都会卡在等锁上。所以宁可留一个没关干净的 Chrome，也要把锁放掉：
**一个卡死的账号比一个野进程严重得多。**

### 第 2 层：为什么上限必须比看门狗短

这是最容易写错的地方：

```
LOCK_WAIT_TIMEOUT (10min) < PUBLISH_TASK_TIMEOUT (30min)
```

反过来的话，等待中的任务会先被看门狗判死，**等锁超时永远轮不到生效——等于没加**。
这条不变量有测试钉着（`tests/test_browser_lock_timeout.py::TimeoutConfigTest`）。

### 第 3 层：看门狗的两个职责

1. `_finish_task` 前检查 `_stuck`：看门狗定论之后，**迟到的成功回调不许改写结论**——
   那等于骗用户说发出去了。
2. 判定后通过 `Event` **立刻通知通道线程**放弃这个卡死线程。**不能靠等一个固定宽限期**
   （实测那样会让通道白等十几分钟，排在后面的任务一直停在「排队中」）。

## 手动中断（用户触发，2026-09 新增）

看门狗是**兜底**，默认要等 30 分钟。可用户等不了——"有些任务太慢了一直卡着"，
所以发布中心每个任务都能**手动中断**（`POST /publish/task/<task_id>/cancel`，
界面在任务表格每行的「中断」按钮；批次级的 `POST /publish/job/<job_id>/cancel`
带 `running=1` 连正在跑的一起停）。

**线程依然杀不掉**，中断改变的是三件事，而不是"杀死线程"：

| 中断做了什么 | 为什么重要 |
|---|---|
| **当场给结论**（标「已取消」，`final=True`） | 界面立刻不再是"发布中"，用户能判断下一步 |
| **立刻放通道走**（复用看门狗那个 `Event`） | 同账号后面排队的任务不用再干等 30 分钟 |
| **真的去打断线程**（两条腿，见下） | 能打断就干净收尾，锁和名额都放掉 |

两条腿一起走：

1. **协作式**——任务线程拿一个 `threading.Event`，在**它自己控制的**等待点上回头看一眼：
   等账号锁、等并发名额（`browser_lock._acquire_cancellable` 把小步轮询切开，
   原来 `acquire(timeout=10min)` 是一口气睡到底，中途叫不醒）。被中断就抛
   `PublishCancelled` / `BrowserSessionCancelled` 干净退出，**一次浏览器都不会开**。
2. **异步式**——上传器是 `async` 的，执行器自己建事件循环、把 `(loop, Task)` 登记到
   `_async_runs`，HTTP 线程用 `loop.call_soon_threadsafe(task.cancel)` 把
   `CancelledError` 抛进正在 await 的协程。**不能**直接跨线程 `task.cancel()`：
   事件循环不是线程安全的。

> ⚠️ `CancelledError` 继承的是 `BaseException`，`except Exception` 接不住。
> 执行器必须把它翻译成 `PublishCancelled`，否则任务会**跳过收尾跑掉**，批次永远不 done。

### 中断之后资源回收干净了吗

看情况，**别假设干净**：

* 排队期间被中断、或者上传器正常响应了取消 → 锁和并发名额都释放了，什么都不用做；
* 线程被压在浏览器里（等一个不再响应的驱动）→ 它**还占着**账号锁和一个并发名额。
  这时中断接口返回的话里已经写明"这个账号可能还被占着，彻底回收资源需重启后端"。
  之后同账号的任务会先卡在等锁上，直到 `LOCK_WAIT_TIMEOUT` 超时。

**为什么不能替它把锁放掉**：`account_lock` 是 `threading.RLock`，只有持有它的线程能
release。硬抢过来（换成 `Lock` 再跨线程 release）更糟——那个线程可能只是**慢**、
并没有死，放锁等于让两个浏览器同时上同一个账号，直接把号踢下线。
宁可等它，也不要踢号。

## 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `SAU_PUBLISH_TASK_TIMEOUT` | `1800`（30min） | 单个发布任务的执行上限 |
| `SAU_LOCK_WAIT_TIMEOUT` | `600`（10min） | 等账号锁 / 并发名额 / profile 锁的上限 |
| `SAU_TENCENT_CLEANUP_TIMEOUT` | `30` | 视频号收尾动作（回写 cookie / 关浏览器）的上限 |
| `SAU_MAX_CONCURRENT_BROWSERS` | `4` | 整机同时开几个浏览器 |

例：大视频上传容易接近看门狗上限时，放宽一点：

```bash
SAU_PUBLISH_TASK_TIMEOUT=3600 ./start.sh backend
```

## 出了事怎么办

**看到某个任务一直停在「发布中」不动** → 别干等，直接点那一行的「中断」。
中断会当场把结论改成「已取消」并放同账号的通道继续跑，不用等 30 分钟看门狗。

**看到「执行超时：超过 N 分钟没有结束，已判定卡住」或「等这个账号的浏览器空出来超过 N 分钟」**
→ 说明有线程卡死了，它**还占着**账号锁和一个浏览器并发名额。

**要彻底回收资源（那个账号下一个任务不想等 10 分钟）就重启后端**：

```bash
./start.sh backend
```

重启时第 4 层会顺手把残留记录标成「已中断」，之后正常提交即可。

> 为什么不能自动回收：锁是 `threading` 原语，只有持有它的线程能释放。
> 线程卡在系统调用里，谁也替它放不了。
> 手动中断也一样——它能保证「结论对、通道不堵」，但**不保证**线程真的停下，
> 所以它替代不了重启，只是让你不必为了"别再卡着"而重启。

## 另一类超时：首轮导航 / 取证截图（**不是**锁的问题）

上面四层防护治的是"卡住不返回"。还有一类超时长得像卡住、其实完全不同：
**一批任务里每个通道的第一条一起挂**，报错是 `Page.goto: Timeout ...` 或
`Page.screenshot: Timeout ...`。2026-09-29 17:14 的现场（job=304531fa，6 条任务）：

* 3 个通道的第一条在同一秒启动 → 同时拉起 3 个 chromium（新进程、磁盘缓存冷、
  DNS/TLS 冷、CPU 互相抢），**这一轮**最慢；
* 快手那条：`goto` 用的是 Playwright 默认的 `wait_until="load"` + 30 秒，
  而同一台机器上它的 cookie 校验第一轮就跑了 32 秒（第二轮 18 秒）→ 导航超时判死；
* 抖音那条：页面进去了、视频也传完了，点「发布」后 3 秒没跳转就进了 retry 分支，
  分支里的调试截图没有自己的超时，等字体等满默认 30 秒抛异常、**异常从 `except`
  冒出去**，把一条"再试一次就成功"的发布写成了截图超时。

现在这三处都收紧了（都在 uploader 里，不动上面的锁/看门狗）：

| 位置 | 原来 | 现在 |
|---|---|---|
| 快手 `goto` | `load` + 30s（Playwright 默认） | `domcontentloaded` + 90s，失败重来一次（`_goto_ks_page`） |
| 快手/抖音 调试截图 | 无 path、无超时、异常外溢 | 5 秒超时 + 落盘 `screenshots/` + 异常只记日志（`_debug_shot`） |
| 抖音「发布」确认 | 等 3 秒，`while True` 无预算 | 等 10 秒，总预算 300 秒，超时才失败并说明原因 |

**怎么区分这两类**：锁/看门狗那类的消息里一定有"等…超过 N 分钟"或"执行超时"，
记录耗时十几分钟；这一类是 `Page.goto` / `Page.screenshot` 超时，记录耗时 1～2 分钟。

还嫌慢的话，调小同时开浏览器的数量（首轮的争抢就来自这里）：

```bash
SAU_MAX_CONCURRENT_BROWSERS=2 ./start.sh backend
```
