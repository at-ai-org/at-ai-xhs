# 小红书页面操作层（at-ai-xhs 改造）

> 基底：（上游 commit `0012d2c`，MIT，见 `PROVENANCE.md`）
> 范围：只针对**小红书**，把"在创作服务平台上做的每一件事"重构成可命名、可重试、可取证的操作。

---

## 一、为什么这样改

上游把整条视频发布链写成 `upload_video_content()` 一个大函数（79 行、`while True` 套 `while True`）。
页面一改版，你只能看到"发布失败"，不知道坏在哪一步；而且**两处 `while True` 都没有重试上限**，
控件找不到时会永远转下去，不报错也不退出。

改造后：

```
selectors.py   契约层 —— 控件长什么样（21 条契约，多候选回退）
page_ops.py    操作层 —— 找到之后做什么（8 组操作，每步一个 OpResult）
main.py        编排层 —— 一次发布的完整流程 + cookie 会话管理
```

## 四、与上游的行为差异（重要）

1. **不再调用上游的 `check_original_declaration()`**
   该方法名不符实：它的 docstring 写的是"设置**来源转载**声明"，实现也是点「添加内容类型声明 → 来源转载 → 填媒体名称 → 确认」，
   而且上游在视频流程里**无条件**调用它，`repost_source` 默认空字符串 → 等于每次都尝试声明一个空的转载来源。
   改造后：**默认不声明任何内容类型**；需要原创时显式 `--original`。
   如果以后确实要支持转载声明，把那个方法接回来即可（代码仍在，只是不再被视频流程调用）。

2. **等待上传有超时**：默认 600 秒，超时即失败并留截图。不再无声地永远等下去。

3. **提交重试收敛**：不再 `while True` 无限点，改为固定超时 + 明确失败。

4. **致命步骤失败即中止**（避免"发错"比"没发"更糟）：
   `open_publish_page` / `upload_video` / `wait_upload_done` / `fill_title` / `set_visibility` / `set_original` / `set_schedule`。
   其余步骤（话题、合集、封面、校验）失败只告警，继续把笔记发出去。

5. **macOS 兼容**：上游用 `Control+KeyA` 做全选，在 macOS 上无效（应为 `Meta+KeyA`）。操作层按平台自动选择。

## 六、改版应急流程

1. 跑 `selftest`，看是哪条契约 miss；
2. `--debug` 打开有头浏览器，失败时 `screenshots/` 下会有全页截图；
3. **只改 `selectors.py` 里对应条目的 `candidates`**（不要改 `page_ops.py` 的逻辑）；
4. 再跑一次 `selftest` 确认。

上游的对应修复通常也在 `uploader/xiaohongshu_uploader/main.py`，可用 `PROVENANCE.md` 里的方法 diff 跟进。

## 八、实测结论（2026-09，真实账号深自检）

用真实账号跑了深自检（先上传测试视频把编辑器撑出来），把此前所有"待实测"的猜测一次性变成事实。
**必填契约全部通过。**

### 8.1 页面真实行为（三条关键认知）

| 发现 | 说明 |
| --- | --- |
| **控件是分阶段渲染的** | 打开发布页只有上传区；**上传视频并等转码完成后**，标题/正文/话题/定时/合集/发布按钮才会出现。浅自检下它们必然报缺失——这不是页面坏了，是探得太早。 |
| **上传框是隐藏元素** | `<input class="upload-input" type="file">` 的 `vis=False`，靠点击拖拽区触发。任何要求"元素可见"的探测都会漏掉它，**发布流程的 `upload_video` 也会因此失败**。契约层为此增加了 `require_visible` 开关。 |
| **「上传视频」Tab 默认激活** | class 含 `active`。此时点击会被内部 `<span class="title">` 拦截指针事件而超时——先判断是否已激活，需要点时才用 `force=True`。 |

### 8.2 「选择合集」的真实 DOM（本项目核心增量的答案）

```html
<div class="d-popover collection-plugin-popover">
  <div class="collection-plugin-popover-content">
    <div class="item"><div class="item-content">
         <div class="item-label">风景</div>          <!-- 一个合集一项 -->
    </div></div>
    <div class="popover-footer">
      <div class="popover-footer-content">创建合集</div>  <!-- 新建入口，不是选项！ -->
    </div>
  </div>
</div>
```

| 项 | 实测值 |
| --- | --- |
| 触发控件文案 | **「选择合集」**（不是「添加合集」） |
| 出现时机 | **必须先上传视频**并等转码完成 |
| 弹层容器 | `.collection-plugin-popover` |
| 单个合集 | 其中的 `.item`，名称在 `.item-label` |
| 陷阱 | 底部的「创建合集」是 `.popover-footer`，**不能当成合集选项**（已在 `_filter_collection_options` 里排除） |

**实跑结果**：网页端读取合集返回 `共 1 个合集 → ['风景']`。

## 九、模型配置与 AI 生成文案（2026-09 新增）

### 9.1 设置页

菜单 **「设置」**（`sau_frontend/src/views/ModelSettings.vue`，路由 `/#/settings`；
这里原来叫「模型设置」，加入账号会话续期等设置项后改的名，老地址 `/#/model-settings` 仍可用），
只填三个要素：

| 字段 | 说明 |
| --- | --- |
| 服务地址 | OpenAI 兼容的 base_url，填到 `/v1` 一层，程序自动拼 `/chat/completions` |
| API Key | 明文存本机 `settings.json`（权限 600），**接口只回传掩码**；保存时留空表示不修改 |
| 模型名 | 必须是多模态（能读图）的，例如 `gpt-4o-mini` / `qwen-vl-max` / `doubao-1.5-vision-pro` |

另有两个可选字段：**超时**、**额外要求**（追加进提示词，例如"语气活泼、面向 25-35 岁女性"）。

只依赖标准 `requests`，不引入任何厂商 SDK——官方 OpenAI、各类中转、通义/豆包兼容层、vLLM、Ollama 都能直接填。

页面上有 **测试连接** 按钮，会发一个最小请求验证 url/key/model 是否可用，失败时把服务端返回体原样带出来（401 / 404 / 模型名不存在一眼可辨）。

接口：

```
GET  /xhs/settings        读取（api_key 只给掩码 + has_key）
POST /xhs/settings        保存
POST /xhs/settings/test   连通性测试
```

> `settings.json` 已加入 `.gitignore`——里面有明文 key，绝不能提交。

### 9.2 AI 生成标题与正文（首帧 + 尾帧）

发布页的 **「解析首帧+尾帧生成文案」** 按钮：

```
视频 → ffmpeg 抽首帧 + 尾帧 → base64 → 多模态模型 → JSON {title, desc, tags} → 自动填入表单
```

实现：`uploader/xiaohongshu_uploader/ai_copywriter.py`

| 设计点 | 说明 |
| --- | --- |
| 只发两帧 | 首帧决定"点不点进来"，尾帧反映"看完得到什么"；2 张图 token 成本极低、响应快 |
| 抽帧降本 | 输出宽度限制 720px，够模型看懂又显著省 token |
| 尾帧容错 | `-sseof` 偏移量按 `-1 → -0.3 → -0.05` 退让重试；都失败就只用首帧，不阻断 |
| 首尾相同 | 自动检测（字节比对），相同则只发首帧 |
| 输出解析 | 容忍 ```json 代码块和前后废话，抠出第一个完整 JSON |
| 硬约束 | 标题截断 20 字、正文 1000 字、话题 10 个 |
| 防幻觉 | 提示词明确要求"只描述画面中确实能看到的信息，价格/地点/品牌看不清就不要编" |

接口：`POST /xhs/analyze`，传 `{video, hints?}`，返回 `{title, desc, tags, model, frames}`。
它只读视频文件，**不碰小红书账号、不需要 cookie、不占用浏览器锁**，所以可以和发布任务并行跑。

ffmpeg 由 `imageio-ffmpeg` 提供（自带完整静态二进制，免装 brew），已在 `pyproject.toml` 声明。

### 9.3 默认合集

`settings.json` 里的 `default_collection`（默认值 **「风景」**）决定发布页自动选中的合集。
读取接口 `GET /xhs/defaults`；前端在页面加载时填入。找不到同名合同时 `select_collection`
会安全返回 skipped（保持不选），不会乱选。

## 十、两阶段发布流程（2026-09 改造）

### 10.1 为什么要两阶段

第一版是"点按钮 → 直接发布"。加上 AI 生成文案后这就不合适了：
模型写得不对也会直接发出去，而小红书发布后修改成本很高。

现在改成：

```
① 填素材 + 点「提交到队列」
      ↓  立即返回，不阻塞
② 后端队列：AI 解析视频首尾画面 → 生成标题/正文/话题（默认开启）
      ↓
③ 状态停在「待确认」，任务列表出现「确认发布 / 重生成 / 放弃」
      ↓  人工核对，可以直接改文案
④ 点「确认发布（无头）」或「有头浏览器发布」→ 才真正驱动浏览器发布
```

**"点提交"和"真发出去"之间有一道人工闸门**，这是刻意的。

浏览器模式和"改文案、选合集"一样，都是**在弹窗里跟确认一起提交**的：
`POST /xhs/task/<id>/confirm` 的 body 里带 `headless`（前端两个按钮分别传 `true` / `false`），
不传就沿用任务建出来时的默认值（无头）。所以同一条「待确认」任务可以先用无头试、
被风控提示后直接换「有头浏览器发布」再跑一次，不用重新提交素材（见 10.5）。

### 10.2 任务状态机

| 状态 | 含义 | 可做的操作 |
| --- | --- | --- |
| `analyzing` | AI 正在生成文案 | 放弃 |
| `pending_confirm` | **待确认**（闸门就在这里） | **确认发布（无头）** / **有头浏览器发布** / 重生成 / 放弃 |
| `queued` | 已确认，排队等浏览器 | — |
| `running` | 正在发布 | — |
| `success` / `failed` | 终态 | 详情 |
| `cancelled` | 已放弃 | — |

接口：

```
POST /xhs/publish                  阶段一：提交（不发布）
POST /xhs/task/<id>/confirm        阶段二：人工确认后才真正发布（可带改好的文案 + headless）
POST /xhs/task/<id>/regenerate     重新生成文案
POST /xhs/task/<id>/cancel         放弃
```

确认时用**改后的最终值**重新校验（标题非空、≤20 字、定时格式），而不是用提交时的旧值。

### 10.3 文案生成的三条硬约束（实测调优）

| 约束 | 原因 |
| --- | --- |
| 话题 **3-4 个** | 宁缺毋滥，话题过多反而分散流量 |
| 正文**不得出现**"第一帧/尾帧/画面/图片/截图"等词 | 读者不该感觉到"分析"痕迹；要求模型写得像自己拍的 |
| 看不清的（价格/地点/品牌/数字）不编造 | 防幻觉，宁可少写 |

`max_tokens` 从 1200 提到 3000——中文正文 600 字可能超出 1200 token 导致响应被截断。
同时加了**截断抢救**：严格解析失败时用正则从残片里捞出 title/desc/tags，而不是整个丢弃。

### 10.4 端到端实测（演练模式，未真实发布）

### 10.5 有头发布：被风控提示时的退路（2026-09）

小红书对**无头**（headless）浏览器的发布行为更敏感：容易在提交前后弹「操作过于频繁」
一类的风控提示，甚至卡住提交按钮。无头跑得快、不弹窗口，作为默认仍然合适，
但必须留一条"看起来像真人"的退路。所以确认弹窗页脚给了两个按钮：

| 按钮 | 传参 | 行为 |
| --- | --- | --- |
| 确认发布（无头） | `headless: true` | 默认。浏览器在后台跑，不弹窗口，跑得快 |
| 有头浏览器发布 | `headless: false` | `chromium.launch(headless=False)`，本机弹出真实窗口跑完全程 |

| 决策 | 原因 |
| --- | --- |
| 模式在**确认那一刻**才定，不在提交任务时定 | 提交时还不知道会不会被风控；换模式不用重新传素材、不用重生成文案 |
| 后端只认 body 里的 `headless`，不传就沿用任务默认值 | 老前端 / CLI 不带这个字段时行为完全不变（`True`） |
| 有头不改流程，只改 `launch(headless=...)` 一个参数 | 页面操作层、step 结果、dry-run、串行锁全部复用同一套，模式和步骤解耦 |
| 任务列表加「浏览器」列 | 出问题回头看时能分清每条是哪次、哪种模式跑的；「待确认」阶段显示「确认时选」 |
| 状态消息和发布记录都写清模式 | 例如「排队中（浏览器操作串行执行，有头浏览器（本机弹窗））」「已发布成功（有头浏览器）」 |

有头模式的两个前提（踩过才知道）：

- 后端必须跑在**有图形界面的机器**上——远程 ssh 会话里没有显示器，弹不出窗口；
- 窗口要留到流程结束，中途关掉等于任务失败，所以弹窗里明确提示"不要手动操作那个窗口"
  （人盯着窗口时容易顺手去点，会和自动化抢控件）。

契约回归在 `tests/test_xhs_confirm_headed_only.py`：只验证 `headless` 落在任务状态、消息和
发布记录上（线程与记录写入都替身掉），**不开浏览器、不发布**。

## 十一、素材入库与自动重命名（2026-09 修复）

### 11.1 修掉的两个上游缺口

| 问题 | 现象 | 原因 |
| --- | --- | --- |
| **汉名文件名被清空** | 选 `上传测试视频.mp4` 上传后扩展名丢失 | `secure_filename()` 只保留 ASCII，`上传测试视频.mp4` 被清成 `mp4`（连点都没了）→ 后续 ffmpeg 抽帧、平台上传全挂 |
| **`/upload` 不写库** | 工作台上传的文件在「素材管理」里看不到 | 上游只有 `/uploadSave` 写 `file_records`，`/upload` 只存文件 |

修复：

- 新增 `_safe_upload_name()`：清洗后若拿不到合法的"主名.扩展名"，退化成 `video_<时间戳><原扩展名>`，
  保证扩展名永不丢失；`/upload` 和 `/uploadSave` 共用同一套逻辑。
- `/upload` 上传后同步写入 `file_records`（`filename` = 原名，`file_path` = `uuid_原名`），
  两个入口行为一致，素材管理都能看到。

### 11.2 同一个根因的第二种症状：中文被"吃掉一半"（2026-10-09）

11.1 的兜底只拦得住**纯**中文名——那种会被清成 `mp4`（连点都没了），正好落进兜底分支。
**ASCII 开头 + 中文**的名字没被拦住，因为 `12345城市海岸线的日落.mp4` 清洗后是 `12345.mp4`，
主名和扩展名都还在，旧判断直接放行，于是中文被**静默**删掉：

| 上传时的名字 | 11.1 之后的结果 | 现在的结果 |
| --- | --- | --- |
| `城市海岸线的日落.mp4` | `video_20261009_115412.mp4`（名字丢了，但至少看得出来是兜底） | `城市海岸线的日落.mp4` |
| `12345城市海岸线的日落.mp4` | **`12345.mp4`** ← 用户反馈的"只剩下前面的数字" | `12345城市海岸线的日落.mp4` |
| `我的视频 1.mp4` | **`1.mp4`** | `我的视频1.mp4` |
| `C:\fakepath\高空餐厅俯瞰城市天际线.mp4` | **`Cfakepath.mp4`** | `高空餐厅城市天际线.mp4`（取 basename） |

修复：`_safe_upload_name()` 不再用 `secure_filename`，改成自己的白名单
（中文 / 字母 / 数字 / `_` / `-`，其余丢掉；`.` 与路径分隔符不在名单里，所以照样拼不出 `..`），
并给主名加了 50 字符上限（中文 3 字节/字，Linux/APFS 的文件名上限是 255 **字节**，
长标题原本会在 `file.save()` 抛 `ENAMETOOLONG`）。回归测试
`tests/test_upload_filename.py`（11 条，其中 8 条在旧实现下会红）。

> 注意它和**另一条改名路径**的分工：AI 出标题后的重命名走
> `sau_backend_xhs.py::_safe_title_for_filename()`，那一条是**故意**只留中文+数字
> （标题是模型生成的，`《》`、逗号、emoji、英文词都不适合进文件名）。
> 上传时保的是**用户自己起的名字**，所以口径更宽。两条路别混着改。


### 11.2 AI 出标题后自动重命名素材

AI 生成标题成功后，`_generate_worker` 会把素材文件重命名成标题：

```
videoFile/425e347e-...-acde48001122_video_20260925_184544.mp4
        ↓  AI 生成标题「电视没信号时的彩条 谁还记得📺」
videoFile/425e347e-...-acde48001122_电视没信号时的彩条 谁还记得📺.mp4
```

设计要点：

| 决策 | 原因 |
| --- | --- |
| **保留 uuid 前缀** | `/getFiles` 的 UUID 列是从 `file_path` 下划线前那段推断的；整个换成标题会让该列变成无意义的值 |
| **同步 `file_records`** | `filename` 改成标题（素材管理展示的就是它）；没有记录就补一条 |
| **同步任务的 video 路径** | 后面发布用的是重命名后的文件，不能还用旧路径 |
| **同名自动加序号** | `-2`、`-3`……最多到 99，避免覆盖已有素材 |
| **清洗非法字符** | 标题里的 `/`、`\`、`:`、控制字符必须去掉，否则重命名会失败或跑到别的目录 |
| **emoji 保留** | macOS 支持，Finder 里也好看；不强行剥离 |
| 重命名失败不阻断 | 只记 `rename_note`，AI 文案照常进入「待确认」 |

### 11.3 前端回归护栏

`tools/check_vue_bindings.py`：扫描所有 `.vue` 的 `<template>`，
把里面引用的标识符（`:prop="fn"`、`@evt="fn"`、`{{ x }}`）和 `<script setup>` 里的定义做比对，
报出"模板引用了但脚本里没定义"的名字。

**为什么需要它**：本项目两次踩到同一个坑——用脚本按"起止锚点"删除一段废弃代码时，
把夹在中间的**在用函数**（`startPolling` / `doUpload`）一起删掉了。
症状是运行期静默失效（按钮点了没反应、列表不刷新），排查成本极高。

```bash
.venv/bin/python tools/check_vue_bindings.py sau_frontend/src/views/*.vue sau_frontend/src/App.vue
# 退出码 0 = 全部有定义
```

## 十二、推理模型的两个坑（2026-09 实测）

把模型换成会输出思考过程的服务后踩到两个问题，都已加固。

### 12.1 `max_tokens` 被思考过程吃掉

实测该服务返回的 usage：

```
finish_reason: stop
completion_tokens: 2184
  └─ completion_thinking_tokens: 1908   ← 思考占了 87%
```

`max_tokens` 限制的是 **思考 + 正式输出** 的总和。原来设 1200/3000，思考一开销掉大半，
正式输出的 JSON 就写到一半被截断了——表现为 **标题有了、正文截断、话题标签直接没有**。

处理：
- 默认 `max_tokens` 提到 **8000**，并开放到「设置」页（可调 500–32000）
- 提示词里把 **`tags` 的字段顺序挪到 `desc` 前面**：JSON 是按序生成的，
  万一还是被截断，丢掉的是正文尾部（可读、可补），而不是整块话题
- 加**话题兜底**：解析出来 `tags` 为空时，单独发一次很小的纯文本请求补 3-4 个话题，
  结果里会标注"话题由兜底请求补全"

### 12.2 尾帧与首帧相同

`smptebars` 这类**静态图案测试视频**首尾画面完全一致，代码里做了字节比对并自动降级为只发首帧，
同时给出提示（`尾帧与首帧相同，仅使用首帧`）。真实拍摄的视频不会触发。

### 12.3 复测

同一素材连跑 3 次，话题均为 3-4 个，标题正常：

```
tags=['电视彩条','色彩测试','治愈系','解压']
tags=['色彩搭配','解压','配色灵感']
tags=['屏幕检测','色彩测试','数码小技巧','屏幕偏色']
```

## 十三、素材预览 / 日期 / 文案风格（2026-09 修复）

### 13.1 预览只显示"加载中"

**现象**：素材管理点「预览」，弹窗里没有播放器，只有一行文件信息加一句不消失的「加载中...」。

**三个叠加的原因**：

| # | 原因 | 说明 |
| --- | --- | --- |
| 1 | **展示名丢了扩展名** | 自动重命名时把 `filename` 存成了不带后缀的标题，而预览靠 `isVideoFile(filename)` 判断类型 → 判成"未知类型" → 走 `v-else` 只渲染文件信息，压根没有 `<video>` |
| 2 | **假加载提示** | `handlePreview` 里写了一句 `ElMessage.info('加载中...')`，它只是提示、跟真实加载没关系，看起来就像"一直卡在加载中" |
| 3 | **文件名没编码** | 重命名后的素材名含空格/中文/emoji，直接拼进 URL query 会被截断 |

**修复**：
- 重命名时**保留扩展名**（`filename = <标题><扩展名>`）；已存在的 4 条历史记录一次性补上后缀
- `isVideoFile / isImageFile` 改成优先读 `file_path`（磁盘名，一定带后缀），不再依赖可被改写的展示名
- 删掉假的「加载中」提示，换成真正的 `v-loading` + `@loadeddata / @error` 状态，
  加载失败会明确提示"文件可能已被移动或删除，也可能格式不支持"
- 预览 URL 一律 `encodeURIComponent`
- 顺手修了「下载文件」——它指向的 `/download` 路由后端**根本不存在**，现在改走 `/getFile`

### 13.2 上传日期

- `file_records.upload_time` 由 SQLite 的 `CURRENT_TIMESTAMP` 写入，**是 UTC**，
  直接显示会比北京时间早 8 小时（上传于 18:45 显示成 10:45）。
  已在 `/getFiles` 里转成本地时区返回，列名标注「上传时间（本地）」。
- 小红书工作台的素材下拉也加上了上传日期，格式 `文件名 · 大小MB · 2026-09-25 18:45`，
  下拉里就能分辨新旧素材，不用先去素材管理查。

### 13.3 文案风格改为客观

原来的提示词鼓励"写得像你亲身经历一样自然"，结果产出大量情绪表达
（"谁懂啊""太治愈了""腿真的软了""真的会上头"）。用户反馈要**客观**，已重写提示词：

| 要求 | 内容 |
| --- | --- |
| 整体语气 | 客观、克制、信息导向：像在介绍一件东西、讲清一件事，而不是抒发"看完的感受" |
| 明确禁用 | "谁懂啊""绝了""太治愈""上头""绷不住""真的会谢""泪目""心动""挪不开眼""鸡皮疙瘩"等情绪词；不再写"让我想起小时候"式抒情 |
| 写什么 | 视频里实际存在的东西——场景、事物、步骤、参数、用途、适用人群、注意事项 |
| 人称 | 允许平实视角（"这类配色适合…""用它检查屏幕很方便"），但叙述主体是**内容本身**而非情绪 |
| emoji | 可以用，但要克制，不要每段都堆 |

**改后实测**（同一批素材）：

```
标题: 六色条测试信号：显示器自检用
话题: ['色彩条','显示器检测','屏幕校准','测试信号']
正文: 这是一段标准色彩条测试素材，由 6 条竖直色带组成，从左到右依次是红、绿、黄、蓝、洋红、青。
      左上角带时间码… 主要用来给显示设备做快速自检：偏色与色阶…坏点亮点…拖影残影…
      使用上没有门槛：全屏播放，关闭自动亮度与环境光自适应…
```

```
标题: 海上巨浪实拍：慢速下的浪壁变化
正文: 水体接近墨色深蓝，浪头抬升时浪壁变薄，透光后呈现偏青绿的色调…
      常见的几种用法：做壁纸 / 剪辑空镜 / 配色参考（主色深蓝，辅色青绿与白）/ 检查屏幕暗部表现…

## 十四、正文字数上限（2026-09）

用户要求把 AI 生成的正文收窄，最终定为 **不超过 100 字**。

### 14.1 做成设置项，而不是写死

`desc_max_chars`，默认 **100**，在「设置」页可调（30–1000）。
理由：这个数字是内容策略，不是技术常量——想发长文时改配置就行，不用改代码。

- 提示词由 `build_system_prompt(max_chars)` 动态生成，限制和措辞同源，不会两处不一致
- 字数上限**同时**体现在提示词和代码里：提示词只是"请求"模型守规矩，
  `_clamp_desc()` 做硬保证
- 截断优先切在句末标点（`。！？…` 等）上，避免出现半句话；
  切点若过于靠前（不足上限的 60%）就宁可略超，也不留残句

### 14.2 短篇幅下的提示词调整

100 字装不下原来那套"分类阐述"的结构，所以第 4 条要求改成：

- 一段话写完，**不分小标题、不列长清单、不分点**
- 直接说清"这是什么 + 有什么看点或用途"，次要细节全部舍弃
- 保持客观陈述，不出现情绪词
- emoji 最多 1 个，也可以不用

### 14.3 实测

| 素材 | 标题 | 正文字数 |
| --- | --- | --- |
| 彩条测试 | 彩条测试视频，可自检屏幕显示 | 72 |
| 巨浪 | 深海巨浪拍岸的慢镜头质感 | 76 |
| 3D 雪原 | 3D场景演示：雪原土堡聚落 | 68 |
| 曼德博集合 | 曼德博集合放大，无限不重复的细节 | 72 |

改造前的同类输出是 290–330 字，现已稳定落在 100 字以内，且保持客观风格。例：

> 曼德博集合的连续放大过程：绿色主体边缘层层展开，每一级都重复着相似的轮廓，
> 细节却永不重复。色彩由绿、红过渡到蓝紫，适合做壁纸或数学可视化的参考。

### 14.4 前端提示

- 确认发布弹窗的正文框下方显示「AI 按 100 字以内生成」；手改超出时会变成橙色提醒
  （不强制拦截——平台本身允许 1000 字，是否要发长文由人决定）
- 确认发布弹窗底部写明两种浏览器模式的取舍（无头 / 有头），点了有头之后还会提示"不要关那个窗口"，
  见 10.5

## 十五、账号扫码登录修复（2026-09）

### 15.1 视频号「一直加载中」

**现象**：账号管理里添加视频号账号，弹窗卡在「请求中...」，永远不出二维码。

排查下来是**三个问题叠加**，逐个都让界面必然卡住：

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **选择器匹配不到** | 原代码用 `frame_locator("iframe").get_by_role("img")`。二维码 `<img>` 的 `alt` 为空，ARIA 角色不是 `img`，实测**匹配数为 0**，一直等到 30 秒超时才抛异常 |
| 2 | **异常被静默吞掉** | 登录跑在后台线程里，异常直接让线程死掉，SSE 队列永远为空 → 前端永远转圈，连报错都没有 |
| 3 | **短字符串被前端丢掉** | 视频号二维码的 `src` 是相对路径 `/connect/qrcode/xxx`，只有 30 来个字符；前端判断"这串是不是二维码"用的是 `data.length > 100`，**直接被忽略** |

### 15.2 修复

- **服务端统一转成 `data:image/...;base64,...`**（新增 `_normalize_qr()`）：
  相对路径按 iframe / 页面 URL 补全后由服务端下载并转 base64。
  这样前端拿到的永远是可用的 data URL，不用再猜，也不受防盗链影响。
- **选择器改用 CSS**（新增 `_grab_img_src()`，带轮询）：
  `img[src*='qrcode']` → `img[src*='qr']` → `img` 逐级降级。
  实测 `img[src*='qrcode']` 命中 3 个，取第一个即可。
- **异常兜底**：`run_async_function` 整体包 try/except，任何失败都往队列塞 `500`，
  界面明确显示「添加失败」而不是无声转圈。未知平台类型同样返回 500。
- **前端判断改为按协议**：`data:image` / `http` 直接用，纯 base64（>100 字符）补前缀，
  其余记警告。不再依赖长度猜测。
- 抖音 / 快手 / 小红书三处也加了同样的降级链（保留原有定位方式作为首选，
  失败时回退到 CSS 轮询），避免同类问题在其它平台复现。

**实测**：点「确认」后 **4 秒**出现二维码，`data:image/jpeg;base64,...`（61699 字符，
解码后 470×470 的合法 JPEG）。

## 十六、发布中心重构（2026-09）

### 16.1 素材文案存储

发布中心要「选中素材自动带出标题和内容」，但素材原本只存了文件名。新增一张表：

```sql
CREATE TABLE IF NOT EXISTS material_copy (
    file_path  TEXT PRIMARY KEY,   -- 磁盘文件名
    title      TEXT,
    desc       TEXT,
    tags       TEXT,               -- 逗号分隔
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
)
```

- 单独开表而不是往上游 `file_records` 加列——那是上游的表，加列会让后续跟进上游变麻烦
- 写入时机：① 任务流里 AI 生成成功后自动存；② 发布中心点「AI 生成文案」时（`/xhs/analyze` 带 `save=true`）
- 素材重命名时同步改主键
- `/xhs/materials` 直接带上 `title / desc / tags / has_copy`

### 16.2 新界面

```
① 选择素材        从素材库多选 / 上传本地视频
                  每条素材一张卡片，自动带出标题、正文、话题，可单独编辑
                  没有文案的素材给一个「AI 生成文案」按钮
② 发布到哪些平台  四个平台可多选；勾选后选该平台下的账号（也支持多选）
                  没有账号的平台直接提示「请先到账号管理添加」
                  视频号额外有「仅保存草稿」
③ 发布选项        声明原创 / 定时发布（每天条数、时间点、起始天）
                  抖音商品链接折叠进「高级」
④ 发布            显示「共 N 个发布任务」（素材数 × 平台数）
                  任一前置条件不满足就禁用按钮并说明原因
                  执行后逐条列出结果
```

## 十七、抖音登录：为什么不自己写，改为复用上游主线

### 17.1 起因

抖音账号扫码后一直卡「请求中」，折腾了多轮都不通。最后回到上游 README 才看到关键一句：

> **Web 端相关代码仍然保留，但已经不是当前主线，不保证可直接运行，也不保证与当前 uploader/CLI 完全同步。**

`myUtils/login.py` 里的四个平台登录函数**属于这批历史 Web 端代码**。
而抖音恰好是上游主线重构得最完整的一条线（README 功能表里标注「当前主线重构最完整」），
主线实现位于 `uploader/douyin_uploader/main.py`。

### 17.2 上游主线实现好在哪

```python
# uploader/douyin_uploader/main.py
async def _extract_douyin_qrcode_src(page):
    scan_login_tab = page.get_by_text("扫码登录", exact=True).first
    await scan_login_tab.wait_for(state="attached", timeout=60000)
    # 新版抖音创作者中心 (single_tab + animate_qrcode_container) 不再用 aria-label="二维码"。
    qrcode_selectors = [
        'div#animate_qrcode_container img[src^="data:image"]',
        'div[class*="animate_qrcode_container"] img[src^="data:image"]',
        'div[class*="scan_qrcode_login_content"] img[src^="data:image"]',
        'img[aria-label="二维码"]',
    ]
```

| 能力 | 上游主线 | 我们自己写的 |
| --- | --- | --- |
| 二维码选择器 | 精确的 `#animate_qrcode_container` | 靠猜，还踩了"取最长 data URL 结果拿到品牌横幅"的坑 |
| 二维码失效 | **自动点击刷新并重新推码** | 无，过期就废 |
| 短信二次验证 | 检测并等待用户输入 | 无 |
| 登录完成判定 | URL 进 `creator-micro` 且登录标识消失 | 只看 URL 变化 |
| 二维码定位失败 | 提示"直接在有头浏览器扫码" | 直接抛异常 |

### 17.3 改法

`myUtils/login.py` 的 `douyin_cookie_gen(id, status_queue)` 改成**只做适配层**：
调用上游 `douyin_cookie_gen(account_file, qrcode_callback=...)`，
把回调收到的 `image_data_url` 塞进 SSE 队列，成功后写 `user_info`，失败则清掉半成品 cookie 文件。

其它三个平台（小红书/视频号/快手）暂时保留原实现——它们实测能用，
等哪天出问题再按同样方式迁到主线实现（上游对快手 `ks_setup`、小红书 `xiaohongshu_cookie_gen` 也都有主线版本）。

### 17.4 顺带修掉的前端 bug

`AccountManagement.vue` 的 SSE 处理原本是：

```js
if (!qrCodeData.value && data) { ...设二维码... }
else if (data === '200' || data === '500') { ...设登录状态... }
```

两个问题：

1. **状态码被挂在"还没有二维码"后面** —— 二维码一到位，登录结果就永远判不到了；
2. **二维码只认第一张** —— 抖音二维码失效刷新后推来的新码会被丢掉，
   界面一直显示过期那张，用户扫了没反应。

已改成先判状态码、再判二维码，且二维码可被覆盖刷新。

## 十八、抖音登录最终结论（含短信二次验证）

### 18.1 真实卡点：扫码后还有短信验证

状态监控（`_watch_qrconnect_status`）把过程打出来后，一切就清楚了。
成功那次的完整时间线：

```
22:26:49 🧍 请扫码
22:26:55 🔎 扫码状态变化: scanned          ← 用户扫码（6 秒）
22:27:36 🥳 扫码成功，已跳转到 https://creator.douyin.com/creator-micro/home
22:27:39 🧹 临时二维码文件已清理
✅ 抖音登录成功
```

从 `scanned` 到成功隔了 **41 秒**——这 41 秒用户是在手机上做**短信二次验证**。

### 18.2 抖音二维码只有约 60 秒寿命

全程不点击、纯观察 150 秒的实测：

```
t= 50s  new        ← 二维码生成
t=109s  expired    ← 59 秒后自发过期
t=110s  new        ← 页面自己换了新码
```

**这两个事实叠加**就是之前一直失败的原因：二维码寿命 60 秒，
但扫码后还要做短信验证（40 秒以上），稍微慢一点 token 就过期了。
日志里看到过 `scanned` → `expired`（23 秒）而始终没到 `confirmed`，就是这个情况。

### 18.3 无头 vs 有头

一度改成有头模式想绕开二维码过期，但**无头模式下用户看不到短信验证页面，自然也填不了验证码**——
有头并不能让它自动完成，只是多弹一个窗口。所以最终回到无头，
超时后引导用户"自己在浏览器里登一次"。

```python
LOGIN_HEADLESS = True   # myUtils/login.py
```

⚠️ 这一节只针对**登录**。**发布**另有「有头浏览器发布」按钮（见 10.5）——
那里弹窗口是用户主动选的退路（避风控），和"登录用有头绕不过短信验证"是两回事。

### 18.4 超时提示必须带登录地址

120 秒没等到登录成功时，后端会推一条 `msg:` 消息给前端，
前端在弹窗里用一个 `el-alert` 显示（而不是只丢一个"添加失败"）：

```
⏰ 登录没有完成
   等待扫码登录超时（120 秒内未检测到登录成功）。
   建议先在自己的浏览器里打开 https://creator.douyin.com/ 手动完成登录
   （包括短信验证），登录成功后再回来添加账号。
```

四个平台的登录地址：

| 平台 | 地址 |
| --- | --- |
| 小红书 | https://creator.xiaohongshu.com/login |
| 视频号 | https://channels.weixin.qq.com/login.html |
| 抖音 | https://creator.douyin.com/ |
| 快手 | https://cp.kuaishou.com/ |

SSE 协议上加了一个 `msg:` 前缀（`data: msg:xxx`），前端优先处理它——
它比二维码更紧急，用户照着它才能自己把登录走完。

已经手动登录过的用户，也可以用账号管理里的**「上传Cookie」**按钮把 cookie 导入，
不必重新扫码。
