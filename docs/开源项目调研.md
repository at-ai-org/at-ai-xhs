# 开源项目调研 · 小红书视频笔记发布工具

> 目的：确认"本地视频 + AI 生成文案 + 自动选合集 + 定时发布"这四个诉求，GitHub 上有没有现成合适的项目可以直接用/改/抄。
> 方法：GitHub Search API 检索 20+ 组关键词 → 40+ 个候选项目 → 对其中 15 个做 **README + 源码级**关键词核验（`合集/collection`、`视频/video`、`定时/schedule`、`LLM/AI`）。
> 标注约定：✅ = 已核实支持 ⚠️ = 文档提及未逐行核实 ❌ = 已核实不支持

---

## 一、结论先说

**没有找到一个能直接满足你需求的现成项目。** 但也不是从零开始：

| 你的需求 | 开源现状 | 结论 |
| --- | --- | --- |
| 选择本地视频并发布成**视频笔记** | **充分**，至少 8 个项目支持，含 1.6 万★ 的成熟实现 | 直接复用，不用自己写 |
| **定时发布** | **充分**，多个项目都实现了，且都验证了平台 1 小时 ~ 14 天的窗口 | 直接复用 |
| AI 生成标题/正文 | **部分**：有 5+ 个项目做"输入主题/产品 → 生成文案"，但**没有一个是从视频内容本身理解的** | 需要自研 |
| 自动选**合集** | **完全空白**：15 个项目里零命中，代码级扫描确认 | 必须自研，也是你的差异化 |

一句话：**"发布"这件事开源已经帮你解决了，"看懂视频写出文案"和"选合集"没人做过。**

## 三、两条技术上真正不同的路线

调研中最有价值的发现：社区里存在**两种完全不同的发布技术路线**，不是同一件事的不同实现。

### 路线 A · DOM 自动化（Playwright / CDP）

**代表**：`xiaohongshu-mcp`、`social-auto-upload`、`XiaohongshuSkills`、`xhs_ai_publisher`、`Spreado` —— 15 个项目里 13 个走这条路。

- 做法：真实浏览器打开创作服务平台，模拟点击/输入
- ✅ 不需要逆向任何签名，实现直观，账号行为特征更接近真人
- ❌ **页面一改版就坏**。`XiaohongshuSkills` 的 README 里专门有一条更新记录：

  > **创作者中心兼容修复**：适配 2026 年 2-3 月发布页 DOM 变动（发布按钮、定时开关、日期输入、多图上传等待、正文编辑器）

  这一行就是这条路线的风险说明书，也说明**选择器是长期维护成本**。

### 路线 B · 签名直连创作平台内部 API

**代表**：`ReaJason/xhs`（2,212★，"基于小红书 Web 端进行的请求封装"）→ 被 `comeonzhj/Auto-Redbook-Skills` 以 `vendor/xhs_publish_runtime/` 的形式内嵌使用（内含 `xhs_creator_sign.js`、`js/sign.js` 等签名脚本）。

- 做法：JS 逆向出签名算法，直接 POST 平台内部接口
- ✅ 快、稳（不受 DOM 改版影响）、可批量
- ❌ 签名算法一旦变更全线失效；请求特征更"机器"，风控暴露面更大
- 📌 我核验了它的发布 payload：字段有 `title / desc / type / postTime / topic`，**没有 collection（合集）字段**

**给本项目的判断**：走 A。理由——发布频率极低（一天几条），DOM 自动化 1–5 分钟的上传耗时可接受，不值得为这点速度去承担签名逆向的长期维护成本和更高的风控暴露。这也印证了原方案里"发布执行器做成可替换后端"的价值：真到 A 走不通时，B 是备胎。

## 四、逐项核验的证据

### 4.1 「合集」——确认是空白

对 15 个项目做了代码级扫描（抓取 publish/upload/collection 相关源文件后全文匹配 `合集|collection`）：

| 项目 | 小红书文件命中 | 别处命中 |
| --- | --- | --- |
| xiaohongshu-mcp | **0** | — |
| social-auto-upload | **0** | ✅ `uploader/ks_uploader/main.py`：快手「加入合集」Ant Design Select |
| matrix | **0** | ✅ `tencent_uploader/main.py`：视频号「添加到合集」（部分被注释） |
| Auto-Redbook-Skills | **0** | 发布 payload 无 collection 字段 |
| xhs_ai_publisher | **0** | — |
| XiaohongshuSkills | **0** | — |
| DeliciousBuding/xiaohongshu-skill | **0** | — |

**结论**：快手、视频号的合集自动化有人做了，**小红书的没有**。这个功能要么没人需要，要么没人做出来——从合集对小红书流量的实际价值看，更可能是后者。

顺带一个可直接借鉴的**设计印证**：`social-auto-upload` 的快手实现里写着

> 找不到匹配名字的合集选项时按 Escape 收起下拉，保持未选状态直接发布（界面允许留空）

这与我方案 4.4 节"**不确定就不选**"的阈值策略完全一致 —— 说明这个取舍在实战中被验证过。

### 4.2 「视频理解 → 文案」——确认是空白

所有带 AI 的项目，生成的输入都是**主题/关键词/产品信息**，不是视频内容本身：

- `xhs_ai_publisher`：AI 生成标题/文案，但**文件树里没有任何视频相关文件**（163 个文件，`video|视频` 零命中）→ 只做图文
- `xhs_content_agent`：README 明确写着采集时"**自动跳过视频与广告**"，只做图文赛道
- `Auto-Redbook-Skills` / `YYH211/xiaohongshu`：主题 → 文案 → 配图 → 发布

真正做"视频内容理解"的项目都在**别的赛道**：
- `chubbyskills`（1,010★）：视频转文字稿，**字幕优先免 GPU** 的思路值得抄（有字幕轨就不用跑 ASR）
- `hc-tec/my-collection-skills`：Whisper 转写，但目的是把收藏内容存进知识库，不发布

**结论**：视频理解管线（ASR + 关键帧 + OCR → 文案）得自己写。好消息是可以抄 `chubbyskills` 的"字幕优先"降本技巧。

### 4.3 「发布前体检」——有现成轮子，直接复用

原方案 4.3 节设计了一套硬校验（违禁词/极限词/引流词）。调研发现有现成的：

- [`yuwen-cool/yuwen-publish-precheck`](https://github.com/yuwen-cool/yuwen-publish-precheck)（754★，**MIT**）：抖音/小红书/视频号发布前 AI 审查，声称"38 篇真实样本校准判定尺度、80+ 条官方原文引文可查证、规则库本地可积累"，且姿态正确——"不承诺过审，不教绕审"
- [`CCCpan/chinese-sensitive-words-mcp`](https://github.com/CCCpan/chinese-sensitive-words-mcp)（113★，**MIT**）：中文违禁词检测 MCP，带风险分级 + 安全替换建议

**建议**：体检环节直接接这两个之一，把自家精力省下来做合集和视频理解。

## 五、推荐怎么用这些项目

### 方案一（推荐）：站在 xiaohongshu-mcp 肩膀上，只补两个空白

```
[自研] 视频理解管线  →  [自研] 文案生成 + 合集匹配（含合集清单抓取）
                              ↓
                    [复用] xiaohongshu-mcp 做发布执行
                    （视频上传 / 标题 / 正文 / 话题 / 定时 1h-14d / 可见范围 / 原创声明）
```

- **理由**：`xiaohongshu-mcp` 是 1.6 万★、Apache-2.0、最近仍在更新（2026-09-22），已经把你 4 个诉求里最"脏"的两个（视频上传 + 定时）做完了，而且它自己就是以 HTTP MCP 暴露的，**不用改它的代码，当服务调就行**
- 你只需要写：视频理解、文案生成、合集匹配，以及一层"编排"把它们串起来
- 工作量比全自研小一半以上，而且踩坑成本被前人吃掉了
- 副作用：最终产物天然就是个 MCP 工具，DSH / Claude Code 都能直接用

### 方案二：纯 Python 单栈自研发布器

如果你不接受 Go 二进制/Docker 依赖，想要纯 Python 单栈：

- 主要参考 [`white0dew/XiaohongshuSkills`](https://github.com/white0dew/XiaohongshuSkills)（MIT，3.4k★，**唯一明确在跟 DOM 改版的项目**，更新到 2026-09-24）
- 辅以 [`DeliciousBuding/xiaohongshu-skill`](https://github.com/DeliciousBuding/xiaohongshu-skill)（Apache-2.0）——它的 `publish.py` 里有干净的 `schedule_at`（1h–14d 校验）和**审批闸门**设计，和原方案的"人工确认"思路一致
- 发布选择器仍以原方案 2.2 节的契约为准（多候选回退）

### 无论走哪条路，这两块必须自研

1. **合集自动选择**：无先例。思路迁移参考 social-auto-upload 的快手合集实现（label 锚点定位 Ant Design Select + 找不到就留空）
2. **视频理解 → 文案**：无先例。参考 chubbyskills 做降本（字幕优先），其余按原方案 4.2 节做

## 六、必须注意的三个坑

### 1. 许可证不是小事

| 项目 | 许可 | 能不能抄代码 |
| --- | --- | --- |
| xiaohongshu-mcp / xhs_ai_publisher / DeliciousBuding / matrix / Easel / Spreado | Apache-2.0 | ✅ 可商用，保留声明 |
| social-auto-upload / XiaohongshuSkills / chubbyskills / yuwen-precheck / sensitive-words-mcp / ReaJason-xhs | MIT | ✅ 最宽松 |
| **MatrixMedia** | **GPL-2.0** | ⚠️ **传染性**，闭源项目别碰 |
| **Auto-Redbook-Skills / xhs_content_agent / YYH211 / luyike221** | **无 License** | ❌ **默认"保留所有权利"，不能复制代码**，只能当思路参考 |

`Auto-Redbook-Skills` 那个签名直连实现虽然 2.3k★，但**无许可证 + 内嵌签名逆向代码**，双重不建议直接抄。

### 2. 别抄"采集/搬运/矩阵"类的项目

搜到的很多高星项目（`creatorhub` 2.1k★ "多平台内容监控·采集·**搬运**"、各种 matrix/矩阵分发）是**矩阵号铺量**工具。这类工具和账号被封的距离很近，且与你的"单账号认真做内容"场景不匹配。原方案 9.3 节"不做互动类自动化、不做多账号矩阵"的保守立场值得坚持。

### 3. 星标高 ≠ 适合你

`Agent-Reach`（85,299★）看着最高，实际是"给 AI agent 读全网内容"的工具，与发布无关。真正相关的第一个项目就是 1.6 万★ 的 `xiaohongshu-mcp`。**按需求匹配度而不是星标选型。**

## 七、对原方案的修正建议

基于本次调研，建议对 `docs/设计方案.md` 做三处调整：

1. **§2.1 补一条路线 B**（签名直连内部 API）：记录它的存在与取舍，明确本项目选 A 的理由，并把 B 作为 `PublishBackend` 的第二个备选实现

3. **§4.3 体检环节**：把"自建违禁词库"改为"优先复用 yuwen-publish-precheck / chinese-sensitive-words-mcp（均 MIT），自建词库仅作补充"
